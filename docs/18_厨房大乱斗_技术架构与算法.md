## 1. 继承《游戏宇宙》的架构

当前公开仓库 `hub/server.mjs` 使用单一 3300 入口，围棋/五子棋有独立 Socket.IO 服务，星阵、扫雷和火柴人篮球以浏览器页面运行。厨房 V0.1 应复用 **纯 JS 规则 + Canvas 2D + 同域静态路由** 的工程风格，未来多人版在网关内部增加权威房间。不要为了参考 Delixia 就强行引入整套 3D Babylon.js 和 Bun。


## 3. 固定时间步与游戏状态

计划采用 **20 Hz 固定模拟 tick（50ms）**，Canvas 动画使用 `requestAnimationFrame` 插值显示。高帧率手机与低帧率桌面得到同样的切菜进度、订单时限和配方结果。

~~~js
// 未来 API 设计示例，不是当前已有代码。
const state = createKitchen({ seed: 20261123, mapId: "starter", duration: 150 });
const next = stepKitchen(state, [
  { playerId: "p1", seq: 19, x: 1, y: 0, interact: false },
  { playerId: "p2", seq: 8, x: 0, y: 1, interact: true }
], 0.05);
~~~

推荐结构：

| 数据 | 必要字段 | 约束 |
|---|---|---|
| `players` | id、x/y、朝向、heldItemId、动作进度 | 每人只能持有一件物品 |
| `items` | id、类型、工序状态、位置或持有人 | 全局唯一归属，严禁复制 |
| `stations` | id、工位类型、tile 位置、槽位、工作进度 | 一次只能处理许可数量 |
| `orders` | id、recipeId、deadlineTick、status | 完成/超时只能结算一次 |
| `game` | phase、tick、seed、score、时间 | 相同 seed+输入可回放 |
| `events` | 加工完成、错误上菜、加分、动画提示 | 只用于可视化，不是权威判定 |

## 4. 食物和工位状态机

~~~mermaid
stateDiagram-v2
  [*] --> raw: 食材从箱子领取
  raw --> chopped: 砧板加工
  chopped --> cooking: 汤类合法入锅
  cooking --> cooked: 达到烹饪时长
  cooked --> burnt: 过熟宽限到期
  chopped --> assembling: 沙拉类
  cooked --> assembling: 汤类
  assembling --> plated: 与干净盘组合
  plated --> served: 匹配待完成订单
  burnt --> discarded: 扔垃圾
  served --> [*]
  discarded --> [*]
~~~

上述是概念总图；沙拉不经过灶台、汤必须烹饪，**具体由配方 DAG 决定**。每张配方 DAG 使用输入集合、操作、工作台类型、加工时长和输出物品描述。原子交互遵循“检查持有者/工位状态 → 消费原输入 → 生成输出 → 一次性提交”。两位玩家同时拾取一个盘子时不能各得到一份。

~~~mermaid
flowchart LR
  LET[生菜] --> LC[切生菜]
  TOM[番茄] --> TC[切番茄]
  LC --> AS[装配沙拉]
  TC --> AS
  PL[干净盘] --> AS
  AS --> SERVE[送餐]
~~~

## 5. A* 导航与地图可达性

地图是四连通瓦片网络。工位不可直接站立，算法目标是工作台周边**可互动地板**。无负边权时用曼哈顿启发：

\[
f(n)=g(n)+h(n),\qquad h(n)=|x-x_g|+|y-y_g|.
\]

V0.1 先做 BFS 连通性验收与玩家手动移动；V0.2 在抽屉中展示 A* 最短合法路径；V0.3 的 AI 将把队友阻塞和正在使用的工位加入移动成本。地图编辑器每次保存后应自动测试所有原料箱、砧板、灶台、装盘台和出餐口是否可达。

## 6. 配方任务图与 AI 队友

订单由可以并行的子任务组成。例如一名厨师切蘑菇，另一名切洋葱，再合流入锅。使用**关键路径算法**估计工序最短理论完成时间，判断哪些任务不能拖延。

计划 V0.2 开始加入不依赖外部模型的规则 AI 厨师。对厨师 i 执行任务 j 的预计成本：

\[
C_{ij}=T^{travel}_{ij}+T^{work}_j+
  \lambda\max(0,\widehat{T}^{finish}_{ij}-deadline_j)+\mu T^{congestion}_{ij}.
\]

`Ttravel` 来自 A*，`Twork` 为工位加工时长，第三项是订单逾期风险，最后是走道和工位拥堵。两名厨师时使用贪心/小规模枚举即可；需要更多厨师再比较拍卖或指派算法。

**AI 必须可解释**：例如“选择送汤，因为预计只需 2.5 秒，而订单剩余 12 秒”。提示数字必须由算法真正计算，不能用固定文案冒充推理结果。AI 仅可读取正常玩家能知道的地图、订单和物品状态，不读取未来随机订单。

## 7. Socket.IO 房间方案（V0.3 才实施）

~~~mermaid
sequenceDiagram
  participant C as 浏览器
  participant H as Game Universe 网关
  participant S as 厨房房间权威服务
  C->>H: /play/kitchen/socket.io
  H->>S: HTTP/WS 升级代理
  C->>H: input(seq,tick,move,interact)
  H->>S: 转发操作
  S->>S: 身份/序号/范围校验与固定 tick
  S-->>C: 权威 snapshot(tick,players,items,orders)
  C->>C: 预测与平滑展示
~~~

网络端权威统一结算，客户端发送**操作意图**而不是虚假的得分。多人房间目标是 2–4 人，支持创建、加入、重连、断线状态快照和同步订单。所有拾取/放下动作原子化，输入加单调序号防重放；权限、大小限制、限流、HTTPS/WSS 另行建设。十人大厨房仍需地图、CPU、带宽与真实多人测试，不视为已经实现。

## 8. 开源项目参考映射

- [Let's Cook!](https://github.com/aschahal/lets_cook)：学习 2D 人物、工作台和订单的模块职责；缺明确许可证时不能复制原代码。
- [Delixia](https://github.com/TriForMine/Delixia)：学习 Colyseus 权威房间、地图哈希、订单/工位服务思路；本仓库仍用 Node.js + Socket.IO，**不直接改用其 3D 技术栈**。
- [Overcooked-AI](https://github.com/HumanCompatibleAI/overcooked_ai)：学习 MDP、规划、A*、多智能体分工评估；以独立纯 JS 算法逐步实现，无须强制安装 Python。
- [ChefJeff](https://github.com/belchingleo/ChefJeff)：学习真人如何向 AI 分工与接收解释；AGPL-3.0 源码如需直接集成必须评估网络服务的许可证义务。

算法实验室建议有三张可视化卡：**路径导航（A*）**、**订单依赖（DAG/关键路径）**、**队友决策（任务成本）**。以透明参数和可重复实验作为《游戏宇宙》的特色。
